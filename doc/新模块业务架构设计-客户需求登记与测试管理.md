## 二、总体设计思路

两个新模块均为「登记 → 流转 → 归档」的单据型业务，完全套用现有架构模式：

- **一个主表 + 若干子表**（附件表、关联表、日志表），外键 RESTRICT/CASCADE 策略与现有一致；
- **一个独立路由文件**挂载到 `/api` 命名空间下；
- **前端 列表页 + 详情页 + 表单组件** 三件套，复用 DataTable / SearchableSelect / AttachmentViewer 等公共组件；
- **状态机校验在后端完成**：状态流转合法性、条件必填校验均由接口层强制，前端仅做提示优化。

## 三、模块一：客户需求登记

### 3.1 模块定位

面向售前/售后的客户诉求入口：统一登记客户提出的需求（接口对接、功能定制、输出结果定制），跟踪其从评估到发布的全生命周期。与之互补的是：**运维中心（Issues）面向问题，本模块面向需求**。

### 3.2 数据库设计

#### 表1：需求主表 `customer_requirements`

```sql
CREATE TABLE IF NOT EXISTS customer_requirements (
  id INT AUTO_INCREMENT PRIMARY KEY,
  req_code VARCHAR(50) NOT NULL UNIQUE COMMENT '需求编号（服务端自动生成：XQ-YYYYMMDD-NN，唯一）',
  customer_id INT NOT NULL COMMENT '客户名称',
  requirement_type ENUM('接口对接','功能定制','输出结果定制') NOT NULL COMMENT '需求分类',
  proposed_date DATE NOT NULL COMMENT '需求提出日期（区别于系统登记时间，已确认必填）',
  urgency ENUM('低','普通','高','紧急') DEFAULT '普通' COMMENT '紧急程度',
  status ENUM('待评估','已评估待开发','开发中','已开发待测试','测试中','已测试待发布','已发布','废弃')
         DEFAULT '待评估' COMMENT '当前状态',
  description TEXT NOT NULL COMMENT '需求详情描述',
  publish_version VARCHAR(50) NULL COMMENT '发布版本号（状态=已发布时必填，如 V2.3.0）',
  publish_time DATETIME NULL COMMENT '发布时间（状态=已发布时必填）',
  deprecated_reason TEXT NULL COMMENT '废弃原因（状态=废弃时必填）',
  remarks TEXT NULL COMMENT '备注（需求变更时写入原需求编号等信息）',
  created_by VARCHAR(100) NOT NULL COMMENT '登记人（登录用户自动带入）',
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP COMMENT '登记时间',
  updated_by VARCHAR(100) NULL COMMENT '最后更新人',
  updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '最后更新时间',
  FOREIGN KEY (customer_id) REFERENCES customers(id) ON DELETE RESTRICT,
  INDEX idx_customer (customer_id),
  INDEX idx_status (status),
  INDEX idx_urgency (urgency),
  INDEX idx_requirement_type (requirement_type),
  INDEX idx_proposed_date (proposed_date),
  INDEX idx_publish_time (publish_time)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

> 说明：已确认（2026-09-08）增加独立列
> `proposed_date DATE NOT NULL COMMENT '需求提出日期'`——必填，区别于系统登记时间，**该列保留**。
>
> 建表迁移（V1.2 结论③）：本模块四表为全新表，可直接 `CREATE TABLE IF NOT EXISTS`；但若服务已跑过旧版本（表已存在），`proposed_date` 等新增列需在 `createTables()` 中走 `SHOW COLUMNS` 探测 + `ALTER TABLE ADD COLUMN` 迁移，保证幂等。参考 `server/database.js` 现有迁移写法。

### 3.4 状态机定义与流转规则

```
待评估
  └→ 已评估待开发 ─→ 开发中 ─→ 已开发待测试 ─→ 测试中 ─→ 已测试待发布 ─→ 已发布
  （任意非终态均可 → 废弃，须填写废弃原因）
```

**后端强制校验规则：**

| 规则 | 实现 |
|------|------|
| 允许跳级与回退（须填原因） | 任意 from→to 组合均允许（已确认 2026-09-08）；回退或跨级跳转时必须携带变更原因（reason），写入日志 remark，缺失返回 400 |
| 「已发布」条件必填 | publish_version、publish_time 为空则拒绝并提示具体缺失项 |
| 「废弃」条件必填 | deprecated_reason 为空则拒绝 |
| 需求变更流程 | 将当前需求置为「废弃」并填写原因 → 用户重新登记新需求，新需求的编号及变更说明写入备注 |
| 每次状态变更 | 同步插入一条 customer_requirement_logs |

**备注**：已确认（2026-09-08）允许正向跳级与回退，但每次流转必须填写原因说明，随状态流转接口一并提交并落库到日志表 remark。

### 3.5 API 设计（`server/routes/customer-requirements.js`）

| 接口 | 方法 | 功能 | 要点 |
|------|------|------|------|
| `/api/customer-requirements` | GET | 需求列表 | 分页 + 筛选：customer_id、device_id、requirement_type、urgency、status、proposed_date 范围、publish_time 范围、关键字（编号/描述）；列表需 JOIN 出客户名称与涉及设备汇总 |
| `/api/customer-requirements/:id` | GET | 需求详情 | 主信息 + 设备列表 + 附件清单 + 状态变更日志 |
| `/api/customer-requirements` | POST | 新增需求 | req_code 由服务端自动生成（XQ-YYYYMMDD-NN）；取号须在 `transaction` 内 `SELECT MAX(req_code) ... FOR UPDATE`（限定当日前缀）或捕获 `ER_DUP_ENTRY` 后重试，避免并发撞号；必填校验；事务写主表+设备关联表；created_by 取 `req.user.username` |
| `/api/customer-requirements/:id` | PUT | 编辑需求 | 更新 updated_by；已发布状态下的编辑范围控制 |
| `/api/customer-requirements/:id/status` | PUT | 状态流转 | 允许跳级/回退但须携带变更原因 reason（缺失返回 400）；已发布/废弃时做条件必填校验；写日志（原因落 remark） |
| `/api/customer-requirements/:id/attachments` | POST | 上传附件 | multer + 队列上传至 uploads/OSS，白名单限制文件类型 |
| `/api/customer-requirements/attachments/:attId` | DELETE | 删除附件 | |
| `/api/customer-requirements/attachments/:attId/download` | GET | 下载/预览附件 | 复用现有下载模式（含批量打包参考 temp_batch_download 的 archiver 用法） |

挂载方式（`server/index.js`）：`app.use('/api/customer-requirements', require('./routes/customer-requirements'));`

## 四、模块二：测试管理

### 4.1 模块定位

跨区域协作的模型测试任务单：深圳填写测试任务单发起测试，上海执行测试并回填总结与反馈单附件，测试通过后线下讨论决定是否将该模型升级为产品最新模型（是 → 系统内替换产品模型）。

### 4.2 业务流程

```
【深圳】创建测试任务单（填写升级内容/特点/要点/要求/场景等）
    │  状态 = 测试中
    ▼
【上海】执行测试 → 填写测试总结 + 上传《测试反馈单》附件
    │  状态 = 已测试
    ▼
线下讨论是否升级为产品最新模型
    ├── 是 → 【系统操作】替换对应产品的模型为最新 ──→ 状态 = 通过
    └── 否 → 填写不替换说明 ────────────────────────→ 状态 = 通过（附说明）
                                            （或测试失败）
                                             状态 = 不通过（模型不好/测试未过）
```

### 4.5 状态机与角色操作约束

```
测试中 ──(上海:提交总结+反馈单附件)──▶ 已测试 ──(线下讨论+决策)──▶ 通过
   │                                                          ▲
   │                                                          │ 决策="否"也归为通过(附说明)
   └──(测试失败/模型不好)─────────────────────────────────── 不通过
```

| 操作 | 角色 | 前置条件 | 结果 |
|------|------|----------|------|
| 创建任务单 | 深圳（任意登录用户） | 产品必选 | status='测试中' |
| 提交测试总结+附件 | 上海测试人 | test_summary 非空、至少一份反馈单附件 | status='已测试' |
| 升级决策=是 | 任意登录用户（不限定 admin） | status='已测试' | 替换产品模型 → status='通过' |
| 升级决策=否 | 任意登录用户（不限定 admin） | status='已测试'，decision_note 必填 | status='通过'（附说明） |
| 作废/不通过 | 任意登录用户（不限定 admin） | decision_note 必填（原因） | status='不通过' |

### 4.6 「替换产品模型为最新」的实现口径

需求文档中"替换对应产品的模型为最新"在现有数据模型下有两种落点，**建议方案 A**：

- **方案 A（推荐）**：产品维度的模型版本记录在 `product_versions`（产品迭代版本）。决策"是"时，将产品的当前版本指针指向本次待测模型对应的版本（V1.2 结论②：**upsert + 事务**）：
  - 按 `(product_id, model_version)` **先查询** `product_versions`：存在则 `UPDATE ... is_current`，不存在才 `INSERT`——因表有 `UNIQUE unique_product_version (product_id, version_number)`，**不能直接 INSERT**，否则撞唯一约束；
  - 事务内依次：置同产品旧记录 `is_current=false` → 置目标记录 `is_current=true` → 写 `decision_note` 留痕（"已于 X 时间将产品 Y 的模型由 A 升级为 B"）；事务回调内使用 `conn.query`（参考 `device-bundles.js` 的 `transaction(async conn => {...})`）；
  - 创建任务单时校验 `model_version` 是否已存在（建议提供该产品 `product_versions` 下拉），避免决策时找不到目标行。
- **方案 B**：若模型属于某模块类型，落 `version_releases`（模块类型维度发布库），逻辑类似（新增 release 并标记生效）。

已确认（2026-09-08）：模型归属按产品维度，采用方案 A 实现；后续如出现模块级诉求再扩展方案 B。

### V1.2 评审补充结论（2026-09-08）

基于「系统逻辑可行性 + 可用性」评审，回写三项阻塞性结论：

1. **人员字段（深圳需求人）**：`shenzhen_requester` 改存飞书 `open_id`（`VARCHAR(64)`），新增冗余列 `shenzhen_requester_name`（显示名，列表/详情展示用）。前端用 **`FeishuUserPicker`（单选）**而非 `FeishuMultiUserPicker`（多选），因需求人仅一位；飞书未配置（`feishuEnabled=false` 或通讯录为空）时该组件会 `return null`，须回退为文本录入（参考 `DeviceForm.tsx` 现有兜底）。二者存其一，必填校验 `shenzhen_requester_name`。`shanghai_tester` 保持 `VARCHAR(100)` 手工文本录入。

2. **「替换产品模型为最新」**：按 `(product_id, model_version)` **upsert** `product_versions` + `transaction`。因表有 `UNIQUE (product_id, version_number)`，不能直接 INSERT，需先查后写；事务内依次「置同产品旧 `is_current=false` → 置目标 `is_current=true` → 写 `decision_note` 留痕」，回调内用 `conn.query`。创建任务单时校验 `model_version` 已存在。

3. **建表迁移策略**：新表/新增列统一纳入 `createTables()` 的 `SHOW COLUMNS` 探测 + `ALTER TABLE ADD COLUMN` 迁移（幂等），不能仅依赖 `CREATE TABLE IF NOT EXISTS`。本模块新增列含 `proposed_date`、`shenzhen_requester`、`shenzhen_requester_name` 等。

> 实现注意：`req_code`（`XQ-YYYYMMDD-NN`）取号需在事务内 `SELECT MAX(...) FOR UPDATE`（限定当日前缀）或捕获 `ER_DUP_ENTRY` 后重试，避免并发撞号；事务回调内一律用 `conn.query` 而非全局 `query`。
