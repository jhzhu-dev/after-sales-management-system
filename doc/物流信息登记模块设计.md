# 新模块设计：订单物流信息登记

> 2026-09-24 初版方案（待评审确认后实施）

## 一、现状分析

### 1.1 "订单"在本系统中的现状

| 概念 | 现状 |
| --- | --- |
| 订单实体 | **没有独立 orders 表**。单台设备订单：`devices.name` 存订单号；多合一订单：`device_bundles.bundle_code` 存订单号（`devices.bundle_id` 关联成员） |
| 发货状态 | `devices.status` 枚举含 `已发货`；发货动作 `POST /api/devices/:id/ship`、`POST /api/device-bundles/:id/ship`（校验：生产中 + 出厂资料完善）只写 `shipped_at = NOW()` |
| 订单信息表 Excel | 导入时 `server/services/order-import.js` 已解析出 订单号/订单时间/计划发货时间/运输方式/包装方式/电池信息/订单补充，但**仅用于导入预览展示，未落库**；Excel 原件归档到设备「出厂资料」 |

### 1.2 差距

- 发货之后**只有时间戳**，没有运输方式、包装、电池处理、箱规、承运商等物流档案；
- 订单信息表里评审阶段填写的物流要求（运输方式/包装方式/电池是否取出）随 Excel 沉没，无法在系统中查询、追溯。

## 二、总体设计思路

1. **物流信息挂在"订单号"维度**（一单一档），而不是每台设备一条 —— 与用户需求"在每个订单中加入物流信息登记"一致，也与箱规（多箱）、电池数量（按视觉器/上位机/服务器汇总）天然对齐。
2. 采用"**主表 + 两个子表**"：电池情况、包装规格是变长行，建子表；其余为单值字段。
3. **入口嵌在设备详情 / 多合一详情页**（按订单号自动带出，无则显示"登记物流信息"按钮），二期可选：独立"物流管理"列表页。
4. 与现有发货动作**松联动**：登记物流信息时可勾选"同时将订单下设备置为已发货"（复用现有 ship 校验）；已发货的设备详情页在基本信息区显示发货时间的同时展示物流档案卡片。

## 三、数据库设计

### 3.1 主表 `order_logistics`

```sql
CREATE TABLE IF NOT EXISTS order_logistics (
  id INT AUTO_INCREMENT PRIMARY KEY,
  order_no VARCHAR(255) NOT NULL COMMENT '订单号，对应 devices.name / device_bundles.bundle_code',
  customer_id INT NULL COMMENT '冗余客户，来源于订单下设备/多合一',
  bundle_id INT NULL COMMENT '多合一订单时关联 device_bundles.id，单台订单为 NULL',
  actual_ship_date DATE NULL COMMENT '1.实际发货时间',
  transport_mode VARCHAR(50) NULL COMMENT '2.运输方式：海运/空运/陆运/其他',
  transport_mode_other VARCHAR(100) NULL COMMENT '运输方式=其他时的说明',
  packing_method VARCHAR(100) NULL COMMENT '3.包装方式：木箱/纸箱/珍珠棉/气泡膜等（可自由填写）',
  battery_removed TINYINT(1) NOT NULL DEFAULT 0 COMMENT '电池是否需要取出（订单信息表模板字段）',
  logistics_type VARCHAR(50) NULL COMMENT '6.物流方式：客户货代自提/货拉拉/快递物流/其他',
  logistics_company VARCHAR(100) NULL COMMENT '物流公司/承运商（货拉拉/跨越/…）',
  logistics_no VARCHAR(100) NULL COMMENT '车牌号或运单号（粤123456 / 132654646646）',
  remark TEXT NULL COMMENT '订单补充/备注',
  created_by VARCHAR(100) NULL,
  updated_by VARCHAR(100) NULL,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  UNIQUE KEY unique_order_no (order_no)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

> 订单号唯一 → 保存接口按 `order_no` 做 **upsert**，同一订单重复登记不会产生多条。

### 3.2 子表 `order_logistics_batteries`（4.电池取出和邮寄情况）

```sql
CREATE TABLE IF NOT EXISTS order_logistics_batteries (
  id INT AUTO_INCREMENT PRIMARY KEY,
  logistics_id INT NOT NULL,
  device_type VARCHAR(50) NOT NULL COMMENT '视觉器/上位机/服务器/其他',
  quantity INT NOT NULL DEFAULT 1 COMMENT '数量',
  battery_kind VARCHAR(50) NULL COMMENT '内置电池/纽扣电池/其他',
  handling VARCHAR(50) NULL COMMENT '随机发货/单独邮寄/客户自购',
  remark VARCHAR(255) NULL,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (logistics_id) REFERENCES order_logistics(id) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

示例数据（对应需求原文）：

| device_type | quantity | battery_kind | handling |
| --- | --- | --- | --- |
| 视觉器 | 2 | 内置电池 | 单独邮寄 |
| 上位机 | 1 | 纽扣电池 | 单独邮寄（或客户自购，见待确认③） |
| 服务器 | 1 | 纽扣电池 | 客户自购 |

### 3.3 子表 `order_logistics_packages`（5.包装规格）

```sql
CREATE TABLE IF NOT EXISTS order_logistics_packages (
  id INT AUTO_INCREMENT PRIMARY KEY,
  logistics_id INT NOT NULL,
  box_label VARCHAR(20) NOT NULL COMMENT '箱1/箱2/…，前端自动编号',
  length_cm DECIMAL(8,2) NULL,
  width_cm DECIMAL(8,2) NULL,
  height_cm DECIMAL(8,2) NULL,
  weight_kg DECIMAL(8,2) NULL,
  remark VARCHAR(255) NULL,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (logistics_id) REFERENCES order_logistics(id) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

### 3.4 与订单信息表模板的字段映射

| 模板字段 | 本模块落点 |
| --- | --- |
| 计划发货时间 | （可选增强）主表加 `plan_ship_date`，详情页"计划 vs 实际"对照 |
| 运输方式（货代信息） | `transport_mode` + `logistics_*` |
| 包装方式 | `packing_method` |
| 电池是否需要取出（服务器/上位机/视觉器） | `battery_removed` + `order_logistics_batteries` |
| 纽扣电池是否单独邮寄（填写） | `order_logistics_batteries.handling` |
| 订单补充 | `remark` |

## 四、API 设计（`server/routes/order-logistics.js`）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/order-logistics` | 分页列表；`keyword`（订单号/客户）、`transport_mode`、`ship_date_from/to` 筛选；JOIN 客户名称、订单下设备数 |
| GET | `/api/order-logistics/by-order/:orderNo` | 按订单号取单条（详情页卡片拉取，404=未登记）；返回主表+电池行+箱规行+**订单绑定设备列表** |
| POST | `/api/order-logistics` | 登记（按 order_no upsert，整体替换两个子表行）；body 携带主表字段 + `batteries[]` + `packages[]`；`ship_devices=true` 时顺带将可发货设备置为已发货（事务内，返回 shipped/skipped 明细） |
| PUT | `/api/order-logistics/:id` | 更新（同 upsert 逻辑，订单号不可变；不改客户/多合一关联） |
| DELETE | `/api/order-logistics/:id` | 删除（订单下存在已发货设备时拒绝，防止误删物流档案） |
| GET | `/api/order-logistics/ship-check/:orderNo` | 发货核对：列出订单下每台设备的可发货状态与不可发货原因（供表单「核对」按钮） |
| GET | `/api/order-logistics/packing-methods` | 历史使用过的包装方式（去重，供表单下拉建议） |

**订单→设备绑定逻辑**（订单在本系统中无独立实体，按订单号反向解析）：

- 单台设备订单：`devices.name = 订单号`（一个订单号可能对应多台单台设备）
- 多合一订单：`device_bundles.bundle_code = 订单号`，成员设备经 `devices.bundle_id` 关联
- 统一查询：`devices d LEFT JOIN device_bundles b ON d.bundle_id = b.id WHERE d.name = ? OR b.bundle_code = ?`
- 前端链接：详情弹窗内每台设备链到 `/devices/:id`；多合一链到 `/bundles/:bundle_id`；列表行「多合一」快捷链

校验：`transport_mode`/`logistics_type`/`handling`/`battery_kind` 用白名单枚举（与前端常量、DB 枚举/注释三方同步，沿用测试任务 priority 的教训）；长度上限对齐现有约定（order_no ≤255，其余 ≤100/255）。

## 五、前端设计

### 5.1 入口（2026-09-24 调整：与出厂资料同模式，取消独立列表页）

1. **DeviceDetail**（单台设备订单）：标签栏新增「物流信息」Tab（模块信息 / 售后服务 / 出厂资料 / 物流信息），Tab 内展示按 `device.name`（订单号）加载的物流档案，无则"登记物流信息"按钮，有则展示 + "编辑"。
2. **BundleDetail**（多合一订单）：标签栏新增「物流信息」Tab（成员设备 / 出厂资料 / 物流信息），按 `bundle.bundle_code` 加载。
3. ~~独立物流列表页~~（已按用户要求移除：侧边栏菜单、`/order-logistics` 路由与列表页均已删除，物流档案仅从设备/多合一详情进入）。
4. 订单→设备的关联展示由现有详情页结构承载（所属多合一、成员设备表），不在物流模块内重复维护。

### 5.2 登记表单（Modal，`OrderLogisticsForm.tsx`）

- 实际发货时间：date input；
- 运输方式：ButtonGroup（海运/空运/陆运/其他），选"其他"出现文本框；
- 包装方式：自由文本（placeholder 提示：木箱/纸箱/珍珠棉…）；
- 电池取出和邮寄情况：`battery_removed` 开关 + 动态行（类型 Select / 数量 / 电池类别 Select / 处理方式 Select / 备注），"添加一行"，可删除；
- 包装规格：动态行（箱N 自动编号 / 长 / 宽 / 高 cm / 重量 kg / 备注），底部自动汇总"共 N 箱，合计 X kg"；
- 物流方式：Select（客户货代自提/货拉拉/快递物流/其他）+ 物流公司文本 + 车牌/运单号文本；"客户货代自提"时后两项可留空；
- 备注 textarea；底部（发货联动勾选，仅订单下仍有生产中设备时显示）。

### 5.3 展示样式

卡片内 `grid grid-cols-1 md:grid-cols-2 gap-4`（沿用测试详情的用户偏好：等宽、保序）；电池行/箱规行用模态内同款表格样式（`bg-card rounded-2xl border-border` 风格）；物流公司展示为 `货拉拉 · 粤123456` / `跨越 · 132654646646` / `客户货代自提`。

## 八、已确认事项（2026-09-24）

1. **运输方式**：海运 / 空运 / 陆运（补入陆运，覆盖货拉拉等国内运输场景）。
2. **包装方式**：自由文本填写；表单提供历史填写值下拉建议（`GET /packing-methods`，同需求分类模式）。
3. **电池处理方式**：单选（随机发货 / 单独邮寄 / 客户自购）。
4. **发货联动**：登记物流时默认勾选「保存后将订单下设备标记为已发货」，表单提供**核对按钮**（调 `/ship-check`，逐台显示可发货/不可发货原因）；仅对「生产中 + 出厂资料完善」的设备生效，事务内执行。
5. **物流档案入口**（2026-09-24 最终口径）：不设独立管理页，仅设备详情/多合一详情的「物流信息」标签页（与出厂资料同模式）。
6. **计划发货时间**：`order_logistics.plan_ship_date` 落库；订单信息表导入成功后自动解析「计划发货时间」写入物流档案草稿（解析不出则跳过，不影响导入）；表单中可手填/修改，详情页与列表页均展示计划 vs 实际。
